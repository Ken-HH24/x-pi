# 章节模板

每个新章节复制并按实际主题调整本结构。章节完成前逐项检查末尾验收清单。

章节文件顶部必须提供网站元数据：

```yaml
---
order: 3
slug: model-events
title: 统一模型事件流
summary: 一句话说明本章得到的能力。
status: current
lab: chapter-03
diffFrom: chapter-02
delta:
  concepts:
    - 新增的核心概念
  behaviors:
    - 相比上一章可观察到的行为变化
  files:
    - 关键文件及职责
diffFiles:
  - src/example.ts
---
```

`diffFiles` 只列最能说明本章变化的文件。学习网站会从相邻 lab 快照生成真实 diff，不要为了完整而把所有测试和夹具都加入。

## 一两句话总结

用一两句话说明本章解决的问题，以及完成后系统新增了什么能力。

## 为什么需要这一章

先给出上一章实现遇到的具体限制，不从抽象定义开始。

## 最小运行效果

展示用户输入的命令、调用方式或初始数据，以及可观察到的输出。

## 模块或数据流程图

使用普通文本代码块绘制 ASCII 图，展示本章最重要的模块关系、调用顺序或状态变化。节点名称必须对应真实代码概念，避免画与实现脱节的理想化架构。

```text
+-------+      +------------+      +--------+
| Input | ---> | Core logic | ---> | Output |
+-------+      +------------+      +--------+
```

可以根据主题绘制模块图、时序图、状态图或数据关系图，但一律使用 ASCII。只有图示确实无法增加理解时才可以省略，并说明原因。

## 分步实现

按数据流顺序解释实现。每一步至少回答：

1. 输入是什么？
2. 关键代码做了什么？
3. 中间状态如何变化？
4. 为什么选择这种设计？
5. 错误或边界条件如何处理？

代码片段只保留正在解释的关键部分，并标明完整代码文件位置。

实现中新增加的函数应带有适当的中文注释，至少说明函数职责。若函数操作的结构或状态不直观，注释中还应尽量给出精简的数据结构、输入输出示例或状态变化；不要用注释机械翻译函数名和语法。

## 关键代码解释

串联本章最关键的函数、类型和状态。重点解释“为什么”和容易误解的边界，不逐行翻译语法。

## 端到端完整例子

至少提供一个具体例子，从真实输入开始，列出关键中间数据，直到最终输出或持久化状态。推荐使用表格：

| 阶段 | 当前数据或状态 |
| --- | --- |
| 输入 | 示例输入 |
| 转换 1 | 第一个中间结果 |
| 转换 2 | 第二个中间结果 |
| 输出 | 最终结果 |

## 错误与边界条件

列出本章实际处理的异常，以及刻意留给后续章节的问题。

## 运行和测试

给出可复制执行的命令、预期结果，以及测试为何能证明本章能力正确。

## 与 Pi 源码的关系

指出对应 package、文件或概念；区分已核对事实、Nano Pi 的教学简化和待后续验证内容。

## 代码规模

列出本章新增核心文件的行数。100–150 行只是常见参考范围，不是硬性上限；重点是让本章形成完整、可理解且范围明确的教学单元。复杂度较高而超过 150 行时，需要说明复杂度来源、实际边界、为何不适合继续拆章，以及读者应如何分段理解。

## 已知限制

明确当前实现不能做什么，避免后续会话误以为已经完成。

## 下一章

说明下一章将由哪个当前限制自然引出。

## 完成验收

- [ ] 有一两句话总结和最小运行效果。
- [ ] 有与真实实现一致、在 Markdown 源文件中直接可读的 ASCII 图。
- [ ] 有关键代码解释，包含设计原因和状态变化。
- [ ] 有从输入到结果的端到端完整例子。
- [ ] 有错误与边界条件说明。
- [ ] 有可执行的测试或验证方法。
- [ ] 有与 Pi 源码的对应关系。
- [ ] 有代码规模、已知限制和下一章入口。
- [ ] 已更新 `README.md`、`docs/progress.md` 和 `docs/source-map.md`。
- [ ] 已保存对应的 `labs/chapter-*` 快照。
